# MC_AI_Player Design Specification

**Date:** 2026-09-10
**Repository:** `neko0115/MC_AI_Player`
**Status:** Implemented pre-release architecture; release and integration gates remain pending
**DC_BOT constraint:** `neko0115/DC_BOT` is read-only for this project until the integration gate passes.

> Status note: this document defines the approved architecture and release gates. The runtime has since been implemented across the major standalone layers described here, but individual release gates are evidence-driven and must not be inferred from this document alone. Use the repository README for the current validated/pending status.

## 1. Goal

Build an independent Minecraft Java Edition player runtime that can play cooperatively with human players. The AI is responsible for high-level decisions only; deterministic runtime code is responsible for movement, pathfinding, inventory, survival, resource gathering, memory, safety, and task execution.

The system must run on a mini PC and target Linux ARM64 Raspberry Pi-class hardware without depending on OCR or frame-by-frame vision for normal gameplay.

## 2. Non-goals

The first release does not implement:

- LLM-per-tick or LLM-per-frame control.
- OCR/vision as the primary Minecraft state source.
- Bedrock Edition.
- Complex PvP.
- Arbitrary free-form commands generated by the model.
- Direct access to DC_BOT databases, Discord tokens, bot instances, or internal objects.
- Direct modification of DC_BOT before MC_AI_Player has passed its standalone and mock-integration gates.
- Shared database files between MC_AI_Player and DC_BOT.
- Automatic export of all Minecraft world data into Moxue social memory.

## 3. External baseline

As verified on 2026-09-10:

- Node.js 24 is the deployment baseline. It is an LTS line and official Linux ARM64 binaries are available.
- Mineflayer is the primary Minecraft Java protocol/runtime candidate.
- Mineflayer currently requires Node.js >=22 in its package metadata.
- `mineflayer-pathfinder` is the primary navigation candidate.
- Exact package versions are pinned by the Phase 0 compatibility probe and lockfile. Version upgrades are explicit compatibility work, not routine floating updates.

## 5. Core principles

### 5.1 AI decides; runtime plays

The AI may choose goals such as:

- follow a player;
- gather 32 oak logs;
- return home;
- deposit items;
- explore a bounded area.

The AI may not issue low-level key presses, look deltas, raw protocol packets, arbitrary JavaScript, shell commands, or free-form Minecraft action strings.

### 5.2 Deterministic skill allowlist

Every executable action is a registered skill with:

- a stable skill name;
- a runtime-validated argument schema;
- explicit preconditions;
- explicit safety permissions;
- a cancellation path;
- a structured result.

Unknown skills and malformed arguments fail closed.

### 5.3 Safety authority

Authority order:

```text
Safety Policy
  > direct player/admin command
  > critical current task
  > AI decision
  > idle behavior
```

The AI cannot override Safety Policy.

Default v1 policy:

- PvP disabled.
- Generic navigation cannot dig (`canDig=false`).
- Building destruction is denied unless a specific approved skill owns the block mutation.
- Unknown commands are rejected.
- AI timeout/invalid output does not start a new action.
- Emergency stop aborts the active goal and pathfinder.
- Low-health and starvation states can preempt non-critical AI goals.

## 6. Reasoning Isolation Contract

This is a hard release requirement.

High-reasoning model modes are allowed and preferred when they improve decision quality, but hidden/intermediate reasoning must never become gameplay input.

### 6.1 No free-text actuator path

There is no parser that extracts commands or JSON from arbitrary model text.

The following response is invalid as a whole:

```text
I should get wood first...
{"intent":"gather_resource","resource":"oak_log","quantity":32}
```

The runtime must not regex-search, substring-search, strip `<think>` tags, or otherwise guess where a final answer begins.

### 6.2 Provider capability model

A gameplay DecisionProvider must support one of these safe modes:

1. **Separated structured output:** provider SDK/protocol exposes the accepted final function/tool call or schema result separately from reasoning/thought content. Reasoning is discarded before the Decision Gate.
2. **Strict schema-only output:** the provider returns exactly one schema-validated object with no accompanying free text.

Providers/modes that expose reasoning and final answer as an inseparable mixed text stream are not valid gameplay DecisionProviders.

### 6.3 Decision Gate

Only this path may reach Goal Manager:

```text
provider response
  -> provider adapter
  -> final structured candidate only
  -> Decision schema validation
  -> skill allowlist validation
  -> Safety Policy validation
  -> Goal Manager
```

The provider adapter must never return raw model text to the executor.

### 6.4 Fail-closed cases

The runtime holds current safe state and starts no new AI action for:

- text before JSON;
- text after JSON;
- `<think>` content mixed with a final object;
- more than one decision object;
- unknown fields such as `analysis`, `reasoning`, or `thought`;
- unknown intent;
- malformed arguments;
- provider timeout;
- parser exception;
- provider capability mismatch.

### 6.5 Chat separation

Player-facing chat is not the planner's reasoning channel.

A successful decision can optionally produce a small semantic `chat_intent`, but final Minecraft chat text is rendered by a separate ChatRenderer using either deterministic templates or a non-reasoning text path.

Intermediate reasoning is never logged into Minecraft chat and is not persisted in MC Memory.

## 7. Runtime components

### MinecraftAdapter
Owns Mineflayer connection lifecycle and emits normalized observations. It does not decide what to do.

### ObservationBridge
Converts Mineflayer events into bounded internal domain events.

### WorldStateCache
Holds ephemeral state such as nearby entities, player positions, health, food, inventory summaries, current dimension, and recent observations. It is bounded and is not long-term memory.

### SafetyPolicy
Evaluates goal/skill permissions and runtime emergency conditions.

### GoalManager
Owns one authoritative active goal, queue/cancellation semantics, completion/failure transitions, and player/admin preemption.

### SkillRegistry / SkillExecutor
Registers allowlisted deterministic skills and executes them through typed validated arguments.

### MCMemory
Stores durable Minecraft-specific facts: landmarks, storage locations, hazards, routes, player instructions, episodes, and task outcomes.

World/chunk state is not duplicated into the memory database.

### ContextBuilder
Builds a bounded decision request from relevant state, recent events, current goal, relevant memory, available skills, and constraints.

### DecisionProvider
Provider-neutral high-level AI interface. A fake provider is authoritative in tests. Real providers are adapters behind the Reasoning Isolation Contract.

### ControlAPI / EventStream
Local control/status interface for test clients and, later, a thin DC_BOT adapter. Long-running goals return an accepted `goal_id`; API requests do not wait for gameplay completion.

### Telemetry / Replay
Captures structured events and decisions without raw hidden reasoning. Supports deterministic replay tests and incident diagnosis.

## 9. Memory boundary

MC memory and Moxue memory remain separate stores.

Examples that remain in MC memory:

- base coordinates;
- chest coordinates;
- mine locations;
- hazards;
- successful routes;
- task outcomes.

Only explicitly selected, socially meaningful facts may later be exported through a future adapter. No direct cross-database reads or writes are allowed.

## 10. Control contract

Initial local API surface:

```text
GET  /health
GET  /v1/status
POST /v1/goals
POST /v1/stop
GET  /v1/memory/search
GET  /v1/events
```

`/v1/events` uses SSE first. WebSocket is deferred unless bidirectional streaming is demonstrated to be necessary.

Default bind: `127.0.0.1`.

If configured to bind a non-loopback interface, startup requires a bearer token.

## 11. Deployment and platform matrix

### 11.1 Windows is the primary development and E2E environment

The initial development machine may be Windows x64. Windows is expected to host the easiest interactive test setup:

```text
Windows x64 development machine
├─ Node.js 24
├─ MC_AI_Player
├─ controlled Minecraft Java test server
├─ human Minecraft Java client
├─ test/telemetry/debug tooling
└─ optional AI provider connectivity
```

Windows support is therefore required for development, unit/integration testing, observation tests, deterministic gameplay tests, reasoning-isolation tests, and cooperative E2E tests.

Linux x64 remains a required CI/release target so Windows-specific assumptions cannot become architectural dependencies.

### 11.2 Raspberry Pi 3 Model B is the minimum hardware experiment target

Known target hardware supplied for this project:

```text
Raspberry Pi 3 Model B
architecture: aarch64 / ARM64 userspace target
RAM: 1 GB
OS target: Raspberry Pi OS 64-bit
power for release benchmark: stable 5 V / >=2.5 A; 5 V / 3 A preferred
```

The Pi 3B is deliberately treated as a constrained minimum target, not as the machine on which all development must occur. A failure to meet the Pi 3B performance gate does not invalidate the architecture; it becomes a documented minimum-hardware limitation and triggers profiling before any hardware recommendation is changed.

### 11.3 The Raspberry Pi does not run the Minecraft GUI client

Normal MC_AI_Player deployment is headless:

```text
Raspberry Pi OS 64-bit
Node.js 24
MC_AI_Player
Mineflayer
mineflayer-pathfinder
MC memory
```

The Pi does **not** require:

- Minecraft Launcher;
- a graphical Minecraft Java client;
- a desktop session;
- OCR;
- screenshot capture;
- local game rendering.

Mineflayer itself is the Minecraft network client. The Minecraft server sees MC_AI_Player as a connected player.

A real Microsoft/Minecraft account may be required for production connection to an online-mode server. Authentication is a credential/runtime concern and never requires storing account secrets in the repository. Controlled early tests may use a private test server configuration that avoids coupling Phase 0-2 to production authentication.

### 11.4 Pi 3B performance gate

The hardware gate must measure, not assume, viability. Required scenarios are:

- connected idle;
- player follow;
- 32-block navigation;
- 64-block navigation;
- bounded resource search;
- gather resource;
- return home;
- inventory/chest operation;
- AI decision request using a remote provider;
- SQLite memory read/write;
- reconnect;
- at least one sustained cooperative session.

Collect at minimum:

```text
process RSS
CPU utilization
event-loop lag
path calculation duration
path replan count
GC pauses when observable
network latency/reconnect time
memory growth per hour
swap activity
throttling/undervoltage state
```

Initial engineering budgets for the Pi 3B are targets to validate, not claims of measured performance:

```text
normal RSS target: < 500 MB
short peak RSS target: < 700 MB
sustained swap thrashing: forbidden
normal event-loop lag target: < 100 ms for the large majority of samples
unbounded memory growth: forbidden
```

If pathfinding exceeds the hardware budget, tune deterministic parameters before changing architecture:

- path segment length;
- `searchRadius`;
- `tickTimeout`;
- `thinkTimeout`;
- Minecraft view distance;
- WorldStateCache radius;
- replan frequency.

Long routes should be decomposed into bounded local path segments rather than requesting one enormous path search.

### 11.5 Power integrity is part of the benchmark

A Pi benchmark taken while the board is undervoltage-throttled is invalid evidence. Before recording release performance, verify stable supply and no active undervoltage/throttling condition.

### 11.6 Required platform evidence

```text
Windows x64     required: development + E2E
Linux x64       required: CI/release validation
Linux ARM64     required: build/runtime validation
Pi 3B ARM64     required: minimum-hardware experiment gate
Mini PC         required before recommending it as production host
```

The detailed platform execution steps live in `docs/superpowers/plans/2026-09-10-windows-pi-validation.md`.

## 12. Validation phases

### Phase 0 — Contract and compatibility harness
No real gameplay actions. Establish schemas, fake adapters, platform probes, version lock, replay fixtures, and safety/reasoning contracts.

### Phase 1 — Observation only
Connect to a controlled Minecraft server and prove passive observation, reconnect, bounded state, and event normalization.

### Phase 2 — Deterministic gameplay
Implement core movement, follow/stay/stop, survival, inventory, resource gathering, and storage without a real AI provider.

### Phase 3 — MC Memory
Add durable Minecraft memory, bounded retrieval, restart persistence, and retention/deduplication rules.

### Phase 4 — AI DecisionProvider
Connect a real high-reasoning provider only after Reasoning Isolation regression tests pass. The real provider can choose only allowlisted structured decisions.

### Phase 5 — Cooperative gameplay
Validate human instruction -> goal -> deterministic execution -> return/report cycles.

### Phase 6 — Low-power deployment
Run the platform plan on Windows x64, Linux x64, generic Linux ARM64, the known Pi 3B target, and the intended mini PC. Pi testing is headless and never requires Minecraft rendering on the Pi.

### Phase 7 — Soak and chaos
Long-duration sessions plus server restart, disconnect, stuck pathfinder, death, full inventory, absent target, and AI failure injection.

### Phase 8 — Moxue integration dry-run
Use a mock adapter with the proposed future DC_BOT contract. DC_BOT remains unmodified.

### Phase 9 — Integration gate
Only after all prior required gates pass may a separate design/PR be proposed for DC_BOT.

## 14. Read-only DC_BOT compatibility notes

The current DC_BOT architecture supports a future thin integration:

- `tools/` is an external tool boundary.
- External tools communicate through JSON contracts rather than importing internal bot objects.
- Tool invocation is request/response and is inappropriate for multi-hour gameplay.
- Agent Core/EventBus exists, but Minecraft event types are not currently part of it.
- Memory V2 has a Minecraft social/game domain, but it is not a Minecraft world-state database.

Therefore the future integration should be a thin status/goal/stop adapter plus, if needed later, an event bridge. MC_AI_Player remains the owner of Minecraft runtime and Minecraft memory.
